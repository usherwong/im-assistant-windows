# 迭代路线：角色 / 题库 / 对方档案 / 多语言

> 状态：**v0.2（决策已定，待开工）**。人设部分的细节见 [PERSONA.md](PERSONA.md)。
> 本文档把 4 个需求拆成可独立交付的增量，并列出依赖、风险、工时和待决策项。
>
> **v0.2 变更**：R4 因“一期只要中英”而大幅简化——RapidOCR 本来就认中英文，**不需要 Windows 语言包**，
> 也不再有 4b（小语种）这条线。R4 变成纯输出协议改造，难度降到 ★★。

## 0. 一句话结论

4 条需求**都合理、都能实现**，但**不是同一个量级**：

| 需求 | 本质 | 难度 | 建议 |
|---|---|---|---|
| R1 角色/员工档案 | 提示词 + 配置 + 轻 UI | ★★ | 先做，作为一切的地基 |
| R2 换题库（方案 B） | 数据 + 少量 UI 标签 | ★★ | 和 R1 一起做（题库挂在角色上） |
| R3 对方档案 + 对话总结 | 存储 + UI + 多一次模型调用 | ★★★ | 拆成 3a / 3b 两步 |
| R4 多语言（中文显示 / 原文填入） | 输出协议 + **OCR 语言覆盖** | ★★★★ | 拆成 4a(英语) / 4b(其他语言) |

R4 有个**隐藏硬依赖**：现在 OCR 只认中英文（RapidOCR 自带 zh/en 模型）。西班牙语/法语等读进来是乱码，
“翻译成中文”和“按原文填回”都无从谈起。所以 R4 不只是提示词改造。

## 1. R1 角色（员工档案）

### 目标
一个“角色”= 我们这边的一个员工：有档案（身份、口吻、目标、筹码/知识库、边界），
用来决定“以谁的身份、从什么立场、带着什么素材”去回复。

### 数据模型（建议）
```json
{
  "id": "emp1",
  "name": "员工1",
  "scene": "recruiting",              // 绑定一套题库（R2）
  "identity": "做 AI 方向的猎头",
  "tone": "轻快、偶尔自嘲，不用「亲/您」",
  "goal": "判断对方是否真在考虑机会，最好约一次 15 分钟电话",
  "materials": ["三个在招岗位：大模型应用/推理优化/Agent", "对方简历要点：..."],
  "boundaries": ["不报具体薪资数字", "不打探现公司机密"],
  "samples": ["我平时发消息的几句原话，用来自动模仿口吻"]
}
```
存哪里：`roles.json`（与 `config.json` 同目录，纯本地）。单角色先跑通，结构上直接支持多角色。
`samples` 一期先留空（自动从历史消息里捞，已有）；`profile` 是完整档案全文，见 1.1。

### 1.1 档案：**卡片 + 全文**两层，不是二选一

用户给的示范档案（林哲远）约 2,400 字 ≈ 1,500 tokens。**整段塞进每次请求不可行**：
一条新消息要调用 3 次（判断→起草→排序），1,500 tokens × 3 就是 4,500 tokens 的固定开销，
还会稀释对话本身。所以分两层：

| 层 | 内容 | 大小 | 何时用 |
|---|---|---|---|
| **卡片（card）** | `voice`（身份/口吻/性格/目标/边界）+ `facts`（结构化事实） | ≤ 400 字 | **每次起草都注入** |
| **全文（profile）** | 用户那份完整档案（职业背景、性格、生活喜好、一天示例…） | 不限 | 界面上看/改；「总结」时按需喂一部分 |

判断规则：
- **单员工、单份档案 → 不需要知识库（RAG）**：全文存着，卡片可让模型一键“压缩成卡片”生成，用户可改；
- **多员工 + 大量资料（岗位库/客户库/历史报告）→ 那时才需要检索层**（卡片 + 检索片段）；
- 现在做 RAG 只会增加复杂度，收益为零。

### 1.2 「问起就查」：档案同时是事实来源（反幻觉）

场景：档案写着“住上海浦东”，对方问“你住哪儿” → 就答浦东；档案里没写的街道**不能编**。

两份示范档案（林哲远 / 达斯汀）放在一起看，暴露了一个关键区别：**事实不是同一种东西**。
有可以随口聊的（职业、住的区、养的猫），有打听才说的（薪资、配偶、租金），
还有**永远不能说出口的**（达斯汀的 2025 泄密与付费约见）。所以档案要分成三块：

| 块 | 内容 | 是否进提示词 | 谁能看 |
|---|---|---|---|
| **`facts`** | 可回答的事实（键值 + 别名） | 命中才注入（≤ 几条） | 模型 + 用户 |
| **`vault`** | 敏感/不可说的事（只记“存在”，不记细节也没关系） | **永不进提示词** | 只有用户 |
| **`constraints`** | 说话红线（“被问私人生活就回‘私人事务，暂无评论’”） | 进提示词（只是规则，不含内容） | 模型 + 用户 |

`vault` 单独隔离很重要：既防止模型说漏嘴，也避免把身份证级别的信息发给模型服务商。
模型只知道“有些事不能聊”，但不知道是什么。

#### `facts` 的单条结构

```json
{
  "id": "residence",
  "label": "现居",
  "value": "华盛顿特区，国会山北区",
  "detail": "租住，月租 3,400 美元",
  "sensitivity": "personal",        // public | personal | secret(→ 必须放 vault)
  "reveal": "on_ask",               // proactive(可主动提) | on_ask(问才说) | never
  "as_of": "2026-11",               // 这条事实的时效
  "aliases": ["住哪", "地址", "where do you live", "address", "租金"],
  "group": "residence"              // 分组：basic/contact/career/education/family/money/habits/health
}
```

字段说明：

| 字段 | 为什么需要 | 例子 |
|---|---|---|
| `value` / `detail` | 一句话答案 + 补充，注入时只发这两段 | `华盛顿特区` / `国会山北区，租住` |
| `sensitivity` | 决定能不能发、要不要脱敏 | 林哲远的咖啡是 `public`，达斯汀的配偶是 `personal` |
| `reveal` | 决定“主动提 / 问才说 / 永不说” | 职业 `proactive`；住址 `on_ask` |
| `as_of` | 事实会过期（年龄、薪资、租金、职位） | 超过 12 个月就提示模型“别说得太肯定” |
| `aliases` | 检索要中英双语（对方可能用英文问） | `["住哪", "where do you live"]` |
| `group` | 界面分组展示、批量开关（比如“钱”整组不主动提） | `money` |

#### 两份档案的映射（验证 schema 够用）

| 原文 | 落成 | sensitivity / reveal |
|---|---|---|
| 林哲远：上海浦东，浦东某街道 | `facts[residence]` value=上海 detail=浦东新区，街道留空 | personal / on_ask |
| 林哲远：橘猫年糕两岁半 | `facts[cat]` | public / proactive |
| 林哲远：不太能吃重辣 | `facts[taste]` | public / on_ask |
| 达斯汀：众议院立法总监，年薪 186,400 | `facts[job]` value=职位 detail=年薪（可只放 range） | public(职位) / personal(薪资) / on_ask |
| 达斯汀：已婚，配偶梅根 | `facts[spouse]` | personal / on_ask |
| 达斯汀：每周四次健身、波本收藏、F-150 | `facts[gym] [whisky] [car]` | public / on_ask |
| 达斯汀：2021 听证会争吵被通报 | `facts[record]`（“有过一次内部通报”）或放 vault | personal / never |
| 达斯汀：平台泄露、付费约见、话术、金额 | **`vault`**（按条记关键词即可） | — / never |
| 达斯汀：“只回‘私人事务，暂无评论’” | `constraints` | 总是进提示词 |
| 达斯汀：讨厌电话、只用邮件/Slack、凌晨发消息 | **`voice.tone`**（不是事实，是说话方式） | — |

结论：**schema 够用**，两份档案（中/英、简单/复杂、有秘密/无秘密）都能装下；
长段落（如“日常一天示例”）不进 `facts`，继续留在 `profile` 全文里按需查看。

#### 检索怎么做（零额外调用）

起草前拿“最新一条消息”去匹配 `aliases` + `label`（中英都匹配，大小写/空格归一），
命中就把该条的 `value + detail`（几十字）追加进提示词；没命中就只发 `voice` 卡片。
一条消息最多注入 3 条事实，避免把卡片撑爆。

#### 反幻觉与时效

- SYSTEM 硬规则：*“档案里没有的事不许编，尤其是住址、单位、收入、家人；不知道就说‘这个见面聊’或反问。”*
- 命中但 `as_of` 超过 12 个月 → 注入时带一句“这条可能过时”，让模型用“大概/还在那边”这种说法，而不是报精确数字。

#### 隐私边界

- `personal` 默认**只在一对一、且对方先问**时用；群聊不主动提（Q16）。
- `vault` 永不进提示词，也不出现在搜索结果里；只有档案面板能看。
- `secret` 级别的事实如果误填进 `facts`，保存时要拦下来并提示“这条更适合放 vault”。

#### 上限与提炼

一个角色的 `facts` 建议 **≤ 30 条**，每条 `value + detail` ≤ 60 字。超了就说明该拆角色或该上知识库。
档案全文（几千字）可以在面板里一键“提炼成 facts 草稿”，用户改完再保存——省手工，但**必须人工过一遍**。

#### 演进

一期关键词匹配（够用、可解释、零成本）；字段多到几十个或资料变成整份文档，再换“小模型字段分类”或向量检索。

### 1.3 角色绑定到会话（Q8 定案）

用户的想法（下拉框选中即固定到该会话，不重选就一直用它）**可行，就按这个做**，落成三条规则：

1. **键**：`chat_key`（会话名规范化）→ `role_id`，落盘到 `contacts.json`；
2. **首次见到某会话**：自动写入“默认角色”（一期只有一个角色，等于全部绑它），之后不再自动变；
3. **用户改选**：下拉选中即写回该会话；不重选永远是上次那个。

边界：
- 角色被删除 → 引用它的会话回退默认角色，并在面板提示一次；
- 会话改名/OCR 抖动 → 沿用现有“相似度合并”；改名会生成新 key，所以**面板必须能改绑**（见 3.1）。

### 关键设计
- **角色是“我”，不是“扮演”**：档案写成关于自己的事实，避免出戏（PERSONA.md 结论 2）。
- **按会话选角色**：和候选人 A 用员工1，和候选人 B 用员工2 是现实场景 → 角色绑到会话，
  默认取“全局默认角色”，可在面板上切换（和「跟随」一起放进标题栏区域）。
- **素材/知识库是二期**：一期 materials 就是几十字到几百字的要点数组；接 RAG 再说。

## 2. R2 换题库（按场景整套换，方案 B）

已在 [PERSONA.md](PERSONA.md) 3.5 节分析：题库是**数据**，换题不动协议层；要改的只有
`guidance_text()`、`CHOICE_LABELS`、`overlay.py` 的 4 处显示。

- 题集与角色绑定：`role.scene` → `QUESTION_SETS[scene]`。
- 首发两套：`intimate`（现有 7 题，保持默认，不破坏老用户）+ `recruiting`（招聘）。
- 每套必须满足契约：1 个 score + 1 个“下一步动作”choice + 1 个“对方需要”choice + 标签表。
- UI 文案跟着题集走：`recruiting` 的 score 显示为「兴趣度」而不是「紧张度」。
- 排序题（`build_rank_question`）通用，只需在 instructions 里带上“当前身份/场景”。

## 3. R3 对方档案 + 对话总结（拆两步）

### R3a 对方档案
- 位置：`跟随` 与左侧会话下拉框之间加一个按钮 → 打开抽屉/面板，预览并编辑“这个人的档案”。
- 内容（建议结构化字段 + 备注）：姓名、公司/职位、来源（预选客户/候选人）、简历要点、诉求、阶段、备注。
- **键 = 会话名**（现在 OCR 出来的会话名），并提供“手动绑定到某个档案”的动作，防止改名/同名串档。
- 作用：档案并入起草提示词（作为“我手上有对方的什么信息”）+ 并入判断上下文（对方背景）。
- 隐私：纯本地存储，但**会随请求发给模型**（和聊天原文一样），需要在文档/设置里写明。

### R3b 对话总结
- 位置：`展开聊天记录` 下方加一个模块：对话内容总结 + 兴趣度/进展判断。
- 触发：**按需**（点“总结”按钮）为默认，结果按会话缓存；新消息到来时标记为“过期”，可一键重算。
  不建议每条消息自动总结——那是第 4 次模型调用，成本和延迟都顶不住。
- 产出结构化一点：`进展`（一句话）+ `对方态度` + `下一步建议` + `风险点`。
- 和 R2 的关系：总结用的是“整段对话级”的判断，而 R2 的题库判断的是“最新一条消息”。

### 共用问题：会话键与手动绑定（Q9 定案）

档案和总结都以 `chat_key`（会话名规范化）为键。会话名来自 OCR，改名/同名会串，所以要有手动绑定：

**推荐做法（三层，从便宜到贵）**
1. **默认自动**：首次见到会话 → 建一条 `chat_key → contact` 记录，名字就是会话名；
2. **自动候选**：打开档案面板时，用“会话名”去匹配已有档案的姓名/公司/别名，
   命中就提示“这像是「张三」的档案，绑定吗？”，一键确认（避免重复建档）；
3. **手动改绑**：面板里提供「绑定到已有档案 / 新建档案 / 解除绑定」三个动作；
   解除后该会话只剩角色、没有对方档案。

数据形状（`contacts.json`）：
```json
{
  "version": 1,
  "contacts": {
    "zhaomm": {
      "chat_key": "zhaomm",
      "role_id": "emp1",
      "display_name": "赵明",
      "company": "某新能源公司",
      "position": "工艺总监",
      "source": "候选池-A",
      "resume": "简历要点…",
      "needs": "薪资涨幅 30%、不想长期出差",
      "stage": "在观望",
      "notes": "聊过两次，对方对加班敏感"
    }
  }
}
```
- 一个会话一条；同一个人开两个窗口（KakaoTalk 一对话一窗口）先各自一条，后续再加“合并档案”动作；
- `role_id` 也放这里（见 1.3），一个会话一条记录同时管“我是谁 + TA 是谁”。

## 4. R4 多语言（显示中文 / 填入原文）—— 一期只做中英

### 需求拆解（Q11 已定）
- 界面上一律**中文**（候选、判断、总结）；
- 点「填入」或「复制」时写进聊天框的是**对方的语言**：对方说英文就填英文，说中文就填中文；
- 混合中英 → 目标语言取**中文**。

### 不需要 Windows 语言包
一期只支持中英：RapidOCR 自带 zh/en 模型，**两种语言都能读**，所以没有 OCR 依赖，
不用装语言包、不用切 OCR 后端。小语种（西语/法语）不进本期，等有真实客户再说。

### 实现思路（输出协议改造）
一次起草调用直接返回成对结果，**不要二次翻译**（慢、且会跑偏）：

```json
{"lang": "en", "replies": [
  {"display": "要不要约个电话聊聊？", "send": "Do you want to hop on a call?"},
  {"display": "行，那先这样", "send": "Sure, let's leave it there"}
]}
```
- `display` 给界面，`send` 给填入/复制；`send` 缺省时退回 `display`（中文场景）；
- 语言判定：让模型在输出里带 `lang`（`zh`/`en`），混合时判 `zh`；**同时以“中文目标”兜底**；
- 解析器扩展：`draft._parse_candidates()` 兼容「字符串数组」和「对象数组」两种形状。

### 影响面
| 位置 | 改动 |
|---|---|
| `core/draft.py` | SYSTEM/USER 增加“显示用中文 + 发送用对方语言”，解析器支持对象数组 |
| `app/overlay.py` | 候选卡片显示 `display`；「填入」「复制」用 `send`；聊天记录仍显示原语言（那是原文） |
| `main.py` | 传 `send` 给 `fill()`；剪贴板同样用 `send` |
| 判断（Jev） | 不变（它看原文，输出中文标签） |

## 5. 依赖关系与里程碑

```
P0 地基（数据模型 + 提示词组装重构）  1.5d   ✅ 已完成
   └─ M1: R1 角色（voice + facts + vault）+ R2 题库  5.5d  ✅ 已完成
        → “以员工1的身份、按职场/招聘场景、答得出档案里的事实、说不了的绝不说”
        ├─ M2: R3a 对方档案 + 角色绑定  2.5d  ✅ 已完成 → “知道对方是谁、我是谁”
        ├─ M3: R3b 对话总结            1.5d  ✅ 已完成 → “能总结这段聊到哪了”
        └─ M4: R4 中英双语             1.5d  → “界面中文、填入原文”
```

**M3 已落地的东西**：
- `展开聊天记录` 下面多了一张「对话总结」卡：点「总结」跑一次（3–10 秒），出五行
  `进展 / 对方态度 / 我方的牌 / 下一步 / 风险`；有答案后按钮变「重新总结」；
- 只在你点的时候跑（不做每条消息自动总结），结果按会话缓存在内存里，重启就没了；
- 有新消息时保留旧总结、标一行「有新消息，建议重新总结」；
- 失败给明确原因（不静默）；
- 总结会带上角色卡（我方能给什么）和对方档案，不写回档案，避免自动污染。

**M2 已落地的东西**：
- 主界面会话行多了一个「角色与档案」按钮（下拉开右边、跟随左边），点开是独立页面；
- 「我的角色」：下拉切换角色（**改选即绑定到这个会话**，之后进来一直用它）、名字、判断题库、
  身份/说话方式/性格/目标、边界、**事实表（一行一条：标签 | 内容 | 补充 | public/personal | 别名）**、
  红线、保险箱（只读，永不进提示词）；保存后下一条消息立刻按新档案生成；
- 「对方档案」：姓名/公司/职位/来源/阶段/对方想要什么/备注，按会话存；
- 判断面板的分数现在带「低/中/高」：`对方投入度 6/9 · 中`，颜色跟着分档走；
- 新文案补了韩语。

**M1 已落地的东西**（`feat/persona` 分支）：
- `app/roles.py`：`roles.json` / `contacts.json` 的读写；种子角色（达斯汀）自动生成；
  `match_facts()` 按中英别名命中事实；`card_text()` 拼 voice 卡 + 红线；`validate()` 拦 secret 混进 facts。
- `core/scenes.py`：`intimate`（原 7 题）/ `work` / `recruiting` 三套题，带标签和 guide 映射；
  自测校验「1 score + 动作 + 需要 + 标签齐全」的契约。
- `core/questions.py`：`guidance_text(answers, scene)` 按题集取标题/分数名（招聘=兴趣度）。
- `core/draft.py`：提示词注入「我的人设」「命中的事实」「对方档案」「关系备注（可选）」，
  SYSTEM 加反幻觉规则（档案里没有的不许编、带日期的可能过时）。
- `core/engine.py`：按角色选题集、把 role/contact 摘要塞进 Jev 的 state、返回 `scene` / `facts`。
- `app/overlay.py`：判断面板按题集显示（对方状态/对方需要/建议动作/对方投入度）。
- 真机验证：默认角色 + `work` 题集跑通，候选会照着事实答“国会山北区”，口吻是短句、不客套。

合计约 **12.5–13 个工作日**（含自测与回归；不含接知识库/RAG）。

**为什么这个顺序**：R1/R2 是提示词与配置，先把“我是谁、按什么标准判断”立起来；
R3 依赖 R1/R2 的上下文才有意义（且要顺带把“角色绑定到会话”落地）；
R4 只改输出协议和 UI 取值，放最后，避免前面的提示词反复返工。

### 6.1 关系字段（`relationship`）怎么处置

用户的直觉是对的：**有了角色档案 + 对方档案之后，`relationship` 这个词很怪**。

现状：`relationship` 同时喂给判断（`build_state` 的 `chat.relationship`）和起草（`relationship: ...` 一行），
默认值是 `romantic partners`——那是给“微信私聊”场景的遗产。

建议按“**降级为可选的关系备注**”处理：
1. 设置页把它从「关系」改名为「关系备注（可选）」，默认**留空**；
2. 空的时候：起草只靠「角色卡 + 对方档案 + 对话」，判断靠题集场景（招聘/采访/亲密）；
3. 填了的时候：原样作为背景补一句（老用户升级无感，仍能写“女朋友/大学同学”）；
4. 新增一个更实用的字段放在**对方档案**里：`关系/阶段`（候选池-A、在观望、已面试…），
   它比一个笼统的“romantic partners”更能指导回复。

一句话：**关系不再是全局开关，而是“某个联系人档案里的一个字段”**。

## 7. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 提示词膨胀 | 角色卡 + 对方档案 + 题集说明 + 对话，容易挤占上下文 | 每块设字数上限；只喂最近 N 条；档案只喂要点 |
| 成本/延迟 | 起草 1 次 + 判断 2 次，再加总结 1 次 | 总结按需 + 缓存；「思考模式」保持默认关 |
| 串档 | 会话名靠 OCR，改名/同名会错 | 手动绑定 + 冲突提示 |
| 小语种 OCR | 一期不做，但用户可能直接收到西语消息 | 界面上给一行“暂不支持该语言”的提示，并保留原文（不瞎翻） |
| 隐私 | 简历、客户资料会进模型请求 | 本地存储 + 可关闭 + 文档写明；默认只发卡片，全文按需 |
| 档案漂移 | 员工档案越长越像“设定集”，和真实说话风格脱节 | 卡片 ≤400 字；`samples` 用真实消息自动校准；定期用真实回复反证 |
| 秘密外泄 | 档案里写了不该说的事（达斯汀那种），模型一激动就说出来 | `vault` 永不进提示词；只说“有些事不聊”；事实检索跳过 secret |
| 冒充风险 | 用真实在任官员/名人做角色，可能被当成冒充 | 角色只用于虚构或明显虚构化的身份；文档与设置页写明责任 |
