# 人设（Persona）改造：可行性与方案

> 状态：**讨论稿 v0.1**（先不实现）。本文档用来对齐结论，后续几轮讨论直接改这里。
> 相关代码：`core/engine.py`、`core/draft.py`、`core/questions.py`、`app/settings.py`、`app/overlay.py`。

## 1. 现在「推荐回复 / 备选」是怎么来的

一次生成是**三段式**，两次 Jev 调用 + 一次起草：

```
对话上下文（最近 N 条，按会话分开存；N = 设置里的「参考上下文」3~30）
  │
  ├─① Jev 判断  core/questions.py: JUDGE_QUESTIONS（7 道题）
  │     literal_question   是否纯字面
  │     true_intent        真实意图（确认你在意 / 表达不满 / 要你行动 / 要解释 / 闲聊 / 收尾）
  │     danger_level       紧张度 0–9
  │     should_reply_now   这条要不要给实质内容
  │     best_action        动作类型（核对记录 / 道歉 / 给承诺 / 解释 / 表达理解 / 少说 / 约安排）
  │     she_needs          对方需要什么
  │     tension_resolved   紧张是否已化解
  │     → 经 questions.guidance_text() 压成中文小抄
  │
  ├─② 起草 3 条  core/draft.py: draft_candidates()
  │     SYSTEM：你是「me」本人在打字。不是助手/客服/作文；不复述、不排比、不客套、
  │             句尾不加句号、三条是同一个人的三种心情（长短不一）
  │     USER  ：relationship + 对话原文 + 防注入提示 + 我平时说话的样本（自己历史消息）
  │             + style（设置里的「说话风格」）+ 群聊 reply_to + ① 的判断小抄
  │     temperature = 1.2（故意高，为了不像模板），max_tokens 400（开思考 4000）
  │     出口硬过滤 _sanitize()：去重 / 不许原样复读对方的话 / 注入消息里出现过的候选直接丢
  │
  └─③ Jev 排序  questions.build_rank_question()
        把 3 条当 choice 选项问「哪条最适合当前对话和对方真实需要」，
        同时给出每条胜出概率 probabilities
        → 概率最高的 = **推荐回复**，其余 = **备选 1 / 备选 2**
```

**要点：**「推荐」不是另一次生成，只是 Jev 在同样 3 条里评出的第 1 名（带百分比）。3 条本身就是一次生成出来的三个变体——所以“改造人设”真正要动的是 ②（写什么），③ 只需要跟着调整评价标准。

## 2. 人设为什么能加：模型现在不知道「我是谁」

喂给起草的「我」只有三样东西：

| 现在有 | 来自 | 说明了什么 |
|---|---|---|
| `relationship` | 设置页 | 我和对方是什么关系 |
| `style` | 设置页 | 我说话的口吻 |
| `samples` | 自动从我的历史消息里捞 | 我平时的用词/句长 |

**缺的是：我的身份、我这轮想干什么、我手上有哪些筹码、我的边界。** 这四样恰好就是“人设”，而它们全都不在提示词里，所以现在无论你在猎头场景还是采访场景，模型都按“亲密关系里的本人”来写。

同时，人设跟现有设计不冲突：SYSTEM 里“你是 me 本人，不是助手”已经把“不要演”钉死了。人设应当写成**关于我自己的事实**（我是谁 / 我要什么 / 我有什么 / 我不做什么），而不是“请你扮演一个可爱的猎头”——后者会立刻把输出带成客服腔，正好撞上它明确禁止的「亲 / 您 / 希望 / 加油哦」。

## 3. 四个可插入的层

| 层 | 插什么 | 影响 | 改动量 | 位置 |
|---|---|---|---|---|
| **A. 起草** | 一段「人设 / 目的 / 筹码 / 边界」 | 候选内容立刻变（从“关心你”变成“我这有个 AI 方向的机会…”） | 小（几十行 + 提示词） | `draft.draft_candidates()` 的 user prompt |
| **B. 判断** | 身份/关系放进 state，让 7 道题看到 | 判断更贴合场景（工作关系里不该判“她需要你在意”） | 中（要重写部分判据） | `questions.build_state()` + `JUDGE_QUESTIONS` 文案 |
| **C. 排序** | 一句「按这个身份和目标挑」 | 推荐那条更贴人设 | 小 | `questions.build_rank_question()` |
| **D. 配置/UI** | 人设卡（预设 + 自定义）、按会话记 | 可复用、可切换 | 中偏大 | `app/settings.py` + `app/overlay.py` 设置页 |

## 4. 三个方案

### 方案 A｜最小可用（约 1 天）
- 设置里加三项：`我的身份`（≤200 字）、`这轮目的`、`边界`（如“不报价、不承诺面试时间”）。
- 拼成一段塞进 ② 的 user prompt；③ 的排序 prompt 加一句“按这个身份和目标挑”。
- 判断层不动。
- **效果**：同一段对话切换人设，候选立刻不同；但 Jev 仍按“亲密关系”打分，推荐可能选到最“暖”的那条而不是最有效的。

### 方案 B｜预设人设卡 + 素材（约 2–3 天）
把人设做成卡片，内置 2–3 个模板 + 自定义：

```
名称：可爱猎头          （内置：可爱猎头 / 有简历的记者 / 本人默认）
身份：做 AI 方向的猎头
口吻：轻快、偶尔自嘲，不用「亲/您」
目的：判断对方是否真在考虑机会，最好约一次 15 分钟电话
我手上有：三个在招岗位（大模型应用 / 推理优化 / Agent）、对方简历要点
边界：不报具体薪资、不打探现公司机密
```

关键在「**我手上有**」这一栏——人设不是形容词，是**筹码**。模型能不能自然说出“我这边有份简历可以发你”，取决于它知不知道你有。
附带：人设按会话记住（同一段对话里别来回变）。

### 方案 C｜人设驱动判断（更远）
为不同场景换一套判断题：工作场景问「对机会的兴趣度 / 是否在观望 / 要不要推进到电话」，而不是「她在不在意你」。
这是让“推荐”真正有意义的前提——否则 Jev 仍按亲密关系标准打分，和你在起草里设定的人设会打架。

### 推荐路线
**先 A（含 ③ 的小改）→ 看两轮真实对话 → 再做 B（人设卡 + 素材）→ 最后才考虑 C。**

## 5. 提示词草案（方案 A 的核心，就这一段）

```
我的人设（这是「我」的身份和当前目的，不是让你扮演别人；口吻规则照旧）：
- 身份：做 AI 方向的猎头
- 这轮目的：判断他是不是真在考虑机会，能约一次 15 分钟电话最好
- 我手上有：三个在招岗位（大模型应用 / 推理优化 / Agent）
- 边界：不报具体薪资数字，不打探现公司机密
- 三条候选落在三个不同切入点上（试探机会 / 给具体价值 / 轻一点收尾），
  但都还是我这个人随手打的，不是话术模板
```

注意最后一条：现在 SYSTEM 说“三条是同一个人的三种**心情**”，加人设后建议改成“三种**切入点**”——猎头/记者这种带目的的场景，“心情”维度会显得很飘。

## 6. 待决策（编号固定，后面讨论直接引用）

| 编号 | 问题 | 我的建议 |
|---|---|---|
| **Q1** | 人设写成「我自己的事实」还是「角色扮演」？ | 写成事实（我是谁/要什么/有什么），避免出戏 |
| **Q2** | 只影响起草，还是连「判断」一起影响？ | 先只影响起草（方案 A）；判断留到方案 C |
| **Q3** | 粒度：全局一个人设，还是**按会话**记？ | 按会话（和 zhaomm 用“本人”，和候选人用“猎头”） |
| **Q4** | 要不要「素材」栏（简历要点 / 岗位列表）？ | 要（这是“有简历的记者”这类需求的关键） |
| **Q5** | 三条候选的差异维度：三种**心情** → 三种**策略**？ | 改成策略，更贴目的 |
| **Q6** | `relationship` 要不要跟着改？现在默认 `romantic partners` | 要；工作场景应设成“猎头与被动候选人”，否则语气仍是情侣 |

## 7. 风险与验证

| 风险 | 说明 | 缓解 |
|---|---|---|
| 出戏 | 人设一长，模型容易变客服腔 | 人设 ≤200 字 + 保留“禁止客套词”硬规则 + 出口仍走 `_sanitize` |
| 推荐失真 | 判断层不改时，Jev 用亲密关系标准给猎头话术打分 | ③ 排序 prompt 加身份；最终靠方案 C |
| 上下文挤占 | 人设+素材吃掉 token | 人设精炼到要点；素材只放要点不放大段简历 |
| 与 style 冲突 | style 是“口吻”，persona 是“身份+目的”，同段话里可能互相拉扯 | 提示词里明确分工：persona 管写什么，style 管怎么说 |

**验证方式**：写 `probe/probe_persona.py`——同一段对话跑两套人设，打印 3 条候选、Jev 的 7 个答案、推荐概率，用来对比；比在界面上肉眼试快得多。再攒一组固定样例（猎头/采访/本人）做回归，防止改提示词时退化。

## 8. 结论（v0.1）

1. **可行，且成本不高**：缺口只在起草的 user prompt，不需要动采集、OCR、填入任何一环。
2. **人设应写成“关于我的事实”（身份/目的/筹码/边界），不是“角色扮演”**，否则会破坏现有的“像真人打字”约束。
3. **分三步走**：A（提示词 + 三个设置项，1 天）→ B（人设卡 + 素材 + 按会话记，2–3 天）→ C（人设驱动判断，另议）。
4. **“推荐/备选”的语义不变**：仍是 Jev 在 3 条里排序；人设改的是“写什么”，排序标准要跟着补一句。
5. **代码分支**：人设单独开 `feat/persona`（基于 `telegram-win`），不混进 Telegram 适配分支；等 `telegram-win` 合进 main 后再 rebase。
6. **下一步**：等 Q1–Q6 拍板，尤其是 **Q3（按会话）/ Q4（素材）/ Q5（策略维度）** 三个，定了就能出具体改动清单和工时。
